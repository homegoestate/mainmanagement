# 正式環境核實、相容改造與切換驗收

**本 PR 的授權範圍是原始碼盤點、候選 Rules 與可審查測試。未核准正式 Rules／Auth／資料／權限異動。**

## 1. 先取得真正的正式狀態（可讀取，不先修改）

以有適當 IAM 權限的管理者開啟：

- https://console.firebase.google.com/project/homego-system/database/homego-system-default-rtdb/rules
- https://console.firebase.google.com/project/mainmanagement-1f3d2/database/mainmanagement-1f3d2-default-rtdb/rules

匯出完整 Rules 並記錄專案、instance、取得時間、SHA256、部署者／歷史版本。也可在已登入 gcloud 的受控電腦執行 `node tools/export-live-rules.mjs`。此工具只有 GET `/.settings/rules.json`；不讀業務資料、不寫規則、不在輸出顯示 token 或 Rules。輸出保存在被 git 忽略的 private 目錄。這不是要求把管理金鑰貼到聊天或 GitHub。

另核實下列項目，資料應私密保管，PR 僅記錄通過／未通過與證據索引：

1. 兩專案的 Auth provider、既有 UID、停用狀態、emailVerified／MFA（若適用）、授權網域。不要因缺映射就刪掉或重建帳號。
2. 兩庫員工原 key、empId 型別、登入別名、在職／離職、裝置核准、主管假別與員工範圍。姓名只供交叉核對，不得自動以同名提升權限。
3. 兩庫頂層路徑與外部使用者（NAS、副本、Worker、Functions、Apps Script、報表）；本 PR 沒有查到的路徑預設拒絕，不能未盤點即上線。
4. 備份及可還原性：包括員工、假勤、申請、設定、既有 Auth 關聯與本機案件／收據／報價。先在隔離環境還原，不用整庫 set 覆寫正式庫作為試驗。
5. 現有 IAM、服務帳戶、App Check、用量與已有稽核／存取紀錄，查看異常下載、寫入、刪除及資料缺漏。沒有紀錄不能反推從未外洩；新啟用紀錄也不能回溯不存在的歷史。

**若仍確認公開讀寫，準備期間漏洞仍存在。** 立即優先安排切換；如出現正在被破壞的證據，應另行決定是否採短暫維護封鎖，不能承諾同時保留匿名舊入口和封住匿名讀寫。不可用「auth != null」或延長公開測試模式充當解法。

## 2. 保留帳號的可信登入銜接（尚待實作與驗收）

主責：後端工程；核定：執行長；帳號清冊核對：指定人事主管。

1. 匯出後建立私密的「原登入別名 → 原員工 key → 每個專案既有 UID」對照。重複／多義項列待核，不自動選第一筆。完全沒有 Auth 的舊員工，經個別核對後新增身分關聯；原業務 key、紀錄與有效帳號不變。禁止自動大量重建。
2. 保留原登入表單與員工別名。若既有 Auth 可驗證原密碼，沿用其 provider；不一致時不可任意覆寫 Auth 密碼。過渡驗證須在可信後端完成，且私密保護舊憑證。禁止前端讀 `users/password`。
3. 因舊憑證可能曾經公開，不能只以舊密碼＋可複製 DID 當高權限首次驗證。先由管理者核實帳號及原裝置，為既有裝置補發可信的裝置憑證／後端 WebAuthn challenge 驗證，再保留原核准關係。後端校驗 challenge、origin、rpId、有效期及防重放；前端本地 WebAuthn 成功本身不算伺服器認證。需要換密碼的帳號單獨安排，不做無差別全員重設。
4. 登入服務做速率限制、統一錯誤訊息、防枚舉、受控密碼雜湊遷移；裝置申請、首次建立、密碼重設、停用、復職全部由後端核對。舊固定管理密碼及可推算開通碼不得簽發有效 token。
5. 驗證成功後，依各專案已核對 UID，分別由該專案 Admin SDK 簽發 custom token，前端在各自 Firebase App 執行 `signInWithCustomToken`。**mainmanagement 的 ID token 不可直接用於 homego-system。** 不把長期 token 放到網址、localStorage 身分提示、未限定接收者的 postMessage。
6. 在隔離 staging 或已受保護的環境由後端建立短效 session，token claim 含 `hg_sid`／`hg_device`；每一 UID 的 ACL 保存 active、role、employeeKey、employeeId（HR 保留原型別）、version、modules、approvals。sessions 保存 active、expiresAt、version、deviceId；devices 保存 active。這些欄位由受控後端獨占寫入。首次 CEO 權限由已核實的專案管理者建立，不從姓名或前端角色推定。
7. 登出／離職／撤裝置時，停用 ACL、撤銷對應 session（必要時提升 version）；舊 refresh token 的回收也需處理。後端每次敏感操作讀取新 ACL；不能只驗 JWT 簽名就跳過撤權。跨專案撤權須驗收兩端失效，不能宣稱原子更新。

## 3. 讀取與寫入改造（尚待實作與驗收）

| 操作 | 新介面／必要伺服器檢查 | 驗收證據 |
|---|---|---|
| 登入、啟動及恢復 | Auth 成功、有效 ACL/session 後才建立訂閱；取本人 selfViews / directory | 舊帳號、舊已核准裝置、新進同仁、離職同仁、錯密碼、撤權都符合預期 |
| 本人假勤 | 按本人原 empId 查詢並分頁；計算完整期間不可只取最後 500 筆 | 舊特休餘額／年資／核定／遞延與對照快照一致 |
| 新增打卡 | 保留原持久操作 key 與讀回去重；候選規則僅收待覆核、serverTimestamp；後端判定結果 | 離線重試、雙擊、定位失敗、伺服器時間、更換員工均不串人或重複 |
| 請假／用車 | 本人 pending 建立，狀態不可自改；後端驗有效日期、數值、重複與業務限制 | 可送出但不自動核准；未知欄位／偽造他人拒絕 |
| 主管核准 | 驗 token／session、在職、對象範圍、假別、禁止自審；重新取原申請；pending→終態且可重試 | 無授權／範圍外／本人／特休一律拒絕；兩人同時審核只成功一次 |
| 特休核准 | 僅核定權者；同一交易核算完整期間、已核定已休／遞延、跨週年、餘額及關聯版本 | 兩個併發核准不可超額；員工資料與申請變更均須防 TOCTOU |
| 主管授權／人事／薪資／裝置 | 後端動作白名單、精確欄位、再次確認最高授權；保留舊主檔與稽核 | 新進人員不必重建其他人；離職、復職不恢復舊主管權或舊裝置 |
| 公務車核准與出勤衍生 | 以原申請 key 去重；核准＋衍生記錄同一原子更新或可重試工作 | 核准成功但衍生失敗可復原，不重複產生 |
| 公告／設定／更正 | CEO 透過後端變更；原值、差異、actor UID、時間、原因及 requestId 寫不可由前端改的稽核 | 讀回確認且未遺失原歷程 |
| 案件／收據／報價／銀行等 | 保留既有資料源；ERP 身分傳遞不能成為雲端權限證明 | 各入口、儲存、匯出、列印、返回總管理照常；Supabase RLS 另外核實 |

後端禁止通用「給 path 和 payload 就替你 Admin SDK 寫入」API。應按動作分開白名單，校驗欄位、筆數、大小、版本及交易；每次都重驗 ACL。凡會跨員工或變更權限者必須有不可由客戶端修改的稽核。Admin SDK 繞過 Rules 的能力不是授權本身。

## 4. 分階段驗收與正式變更

1. 本 PR 僅建立候選方案與 CI。先取得第 1 節證據，再完成登入橋接、讀寫改造、後端服務；每項工作另有審查，不能把本 PR 當全部完成。
2. 建立隔離 staging，匯入去識別但保留相同資料型別／歷史欄位的資料，載入兩份候選規則。不要直接以正式庫試錯。
3. 一般員工、僅病假主管、僅用車主管、撤權主管、執行長、新進員工、離職員工逐一驗收所有實際功能；包含公機、手機、瀏覽器重啟、配額不足、服務中斷及舊頁籤。
4. 逐項檢視 `readiness.json` 的證據；現在均為 false。只有所有必備檢查通過、楊翊晟核准精確變更範圍與時間，才能標為 true。`prepare-deployment.mjs` 只產生兩個精確 instance 的 config，不執行部署；沒有正式自動部署 job。
5. **不可先在仍公開整庫讀寫的正式 RTDB 寫入 `_security`、session 或裝置憑證。祖先的允許不能被子節點拒絕覆蓋，否則 ACL 本身也可被竄改／讀取。** 先在隔離 staging／私密後端完成並核定 ACL 映射；正式切換時先用已驗證安全 Rules 封閉匿名存取，再由 Admin SDK 匯入經核定的最小 ACL 及安全投影，隨即驗收。此間舊根訂閱必然失效，必須由已驗收的可信後端過渡服務承接，或事先核准短暫維護及人工打卡安排。不能承諾單純改 Rules 就零中斷。

   切換窗口先確認可還原快照、排空舊寫入、新版本可用、主管與執行長可登入。清除／更新 service worker 的舊程式快取，要求舊分頁重新載入，但**不清除 localStorage / IndexedDB 業務資料**。
6. 依實際相依順序逐專案套用；ACL 和安全投影須依前項安全順序準備，禁止在開放根權限期間先行寫入。每一步驗證一般員工可打卡／請假、主管可在範圍內審核、CEO 可做主檔及特休、未登入必拒絕。不得只看 Firebase 警告消失就算完成。
7. 上線後以獨立認證測試帳號及事先指定的驗收資料核對；匿名僅檢查安全的測試路徑 denied，不下載全庫。不往真實員工的假勤新增假紀錄。

## 5. 回退與異常處理

- 保留 Rules 原文、hash、部署版本及前端／後端版本對照；資料快照與 ACL 分開私密備份。
- 回退以「已驗證的安全前端／後端＋安全規則」為單位，不單獨恢復依賴公開讀取的舊前端。
- 若尚無安全舊版可回退，使用受控維護／人工記錄（原操作 key 保留，事後核對補登），不能把 `.read/.write=true` 當回退。
- 新規則下出現 permission denied，先確認 UID、專案、session、scope、資料型別和讀取路徑。禁止用放寬根規則來修登入。
- 出現資料外洩／惡意刪改跡象時，另按事件流程保存紀錄、撤銷高風險憑證、評估影響範圍；本次未取得足以認定外洩的證據。
